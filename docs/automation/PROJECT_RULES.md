# Coffee 2048 — Autonomous Development Rules

## 목적
이 문서는 Coffee 2048을 기존 구현 위에서 안전하게 이어 개발하기 위한 자율개발 운영 규칙이다.

핵심 원칙은 **기존 구현과 자산을 최대한 재사용하고, 사용자가 승인한 마일스톤 범위 안에서는 AI가 필요한 시스템/UI/UX를 스스로 판단해 완료 상태까지 구현하되, 게임 방향을 바꾸는 결정은 멈추고 사용자에게 보고하는 것**이다.

---

## 1. 제품 정체성

Coffee 2048은 다음을 결합한 web-first 게임이다.

- 손맛 있는 2048 퍼즐
- 차분한 카페 운영
- 손님 관계/애정도 메타
- 감성적이고 저자극인 UI/UX

현재의 핵심 플레이 구조는 다음과 같다.

`퍼즐 → 원두/보상 → 로스팅 → 메뉴 제작/진열 → 판매 → 코인/애정도 → 손님/성장`

이 연결을 깨는 방향으로 자동개발하지 않는다.

---

## 2. REUSE FIRST — 가장 중요한 규칙

### 반드시 먼저 재사용 여부를 확인한다
새 기능, 새 UI, 새 이미지, 새 데이터 구조를 만들기 전에 저장소에 같은 목적의 것이 이미 있는지 확인한다.

우선 확인 대상:

- `src/features/puzzle2048/**`
- `src/features/lobby/**`
- `src/features/meta/**`
- `src/stores/**`
- `data/**`
- `image/**`
- `public/**`
- `locale/**`
- 기존 `docs/**`

### 금지

- 기존 퍼즐을 확인하지 않고 새 2048 엔진을 만드는 것
- 기존 로비 화면을 확인하지 않고 새 로비를 만드는 것
- 기존 음료 이미지를 확인하지 않고 같은 메뉴 이미지를 새로 만드는 것
- 기존 UI 컴포넌트와 상태 구조를 무시하고 평행 구조를 추가하는 것
- 구버전처럼 보인다는 이유만으로 자산을 임의 삭제하는 것

### 자산 정책

`image/drink/**` 및 기존 런타임 에셋은 우선 재사용 후보로 취급한다.

자산은 다음 4등급으로 분류한다.

1. `REUSE` — 그대로 사용
2. `POLISH` — 보정 후 사용
3. `LEGACY` — 현재 미사용이지만 삭제 금지
4. `NEEDED` — 실제 신규 제작 필요

신규 이미지 제작은 `NEEDED`로 판정된 경우에만 한다.

## 3. 자율 개발 범위

사용자가 예를 들어 `M1~M3까지 구현`이라고 지시하면, 승인 범위 안에서 아래는 별도 질문 없이 스스로 판단해 구현할 수 있다.

### AUTO — 자율 진행 가능

- 승인된 시스템을 완성하는 데 필요한 컴포넌트 추가
- 필요한 UI 상태 추가
- loading / empty / disabled / error state
- 모바일 터치 UX
- 짧은 transition / micro interaction
- 기존 디자인 시스템을 따르는 카드/바텀시트/모달
- 기존 store/action 연결
- 타입 추가
- 테스트 추가
- 작은 리팩터링
- 접근성/레이아웃 보정
- 승인 기능을 위한 자연스러운 UX 흐름 개선

### REVIEW — 구현 가능하지만 완료 후 사용자 플레이 검수 필요

- 새 메타 시스템
- 손님 관계 UX
- 판매 세션 체감 변경
- 성장/업그레이드
- 신규 메뉴 흐름
- 특별 원두
- 저장 연동
- 주요 화면 정보 구조 변경

### STOP — 자동 진행 금지

아래가 필요해지면 구현을 멈추고 `DECISION REQUIRED`로 보고한다.

- 핵심 게임 루프 변경
- 기존 퍼즐 규칙의 의미 있는 변경
- 세이브 호환성을 깨는 변경
- 대규모 상태 구조 교체
- 대규모 폴더/아키텍처 재작성
- 기존 콘텐츠/이미지 대량 삭제
- BM 실결제 구현
- 기존 확정 UI 방향 폐기
- 프로젝트 기술 스택 교체

---

## 4. UI/UX 자동개발 규칙

기능 구현은 기능 코드만 작성하고 끝내지 않는다.

승인 범위를 실제 플레이 가능한 상태로 만들기 위해 필요한 UI/UX는 작업 범위에 포함한다.

### 유지할 방향

- 카드형 로비
- 상단 자원 HUD
- 바텀시트 기반 세부 운영
- 카드형 제작 UI
- 모바일 우선
- 차분하고 premium/cozy한 톤
- 짧고 읽기 쉬운 상태 변화

### 피할 방향

- 관리툴 같은 밀도 높은 UI
- 과도한 팝업
- 과도한 모션/파티클
- 개발자 용어가 노출되는 문구
- 좁은 모바일 화면에서 정보 과밀
- 기존 화면을 이유 없이 새 디자인으로 전면 교체

---

## 5. 무료 개발 원칙

추가 과금이 발생하는 외부 AI/API를 자동으로 호출하지 않는다.

허용:

- 현재 사용 중인 Cursor/ChatGPT/Codex 구독 범위의 직접 작업
- 로컬 Node/Next.js 도구
- Git/GitHub 기본 기능
- 기존 프로젝트 스크립트
- Playwright
- ESLint
- TypeScript

자동 작업이 별도 유료 API 키나 유료 서비스 연결을 요구하면 멈추고 사용자에게 보고한다.

---

## 6. 변경 안전성

- main에서 직접 대규모 작업하지 않는다.
- 의미 있는 기능은 별도 branch에서 진행한다.
- unrelated refactor 금지
- save schema 변경은 version/migration 검토 필수
- 환경변수/비밀키 commit 금지
- 기존 문서 삭제/대규모 덮어쓰기 금지

---

## 7. 기본 검증 게이트

의미 있는 구현 완료 전 최소 검증:

```bash
npm run lint
npm run typecheck
npm run build
```

UI 변경 시 가능하면:

```bash
npm run test:visual
```

기존 프로젝트에 더 구체적인 검증 규칙이 있으면 그 규칙을 우선한다.

빌드 실패 상태에서는 `DONE`으로 보고하지 않는다.

---

## 8. 사용자 검수 지점

AI가 구현을 완료해도 게임의 다음 항목은 사용자 검수를 대체하지 않는다.

- 손맛
- 재미
- 감정 전달
- 화면이 답답한지 여부
- 판매/성장 체감
- 카페 감성

완료보고에는 반드시 `직접 플레이 검수 항목`을 제공한다.

---

## 9. 작업 시작 순서

모든 마일스톤 작업은 다음 순서로 진행한다.

1. `docs/automation/DEV_QUEUE.md`에서 ACTIVE 범위 확인
2. 기존 구현/자산 검색
3. 영향을 받는 파일 목록 작성
4. 구현
5. 검증
6. 자체 회귀 점검
7. 완료보고
8. 사용자 플레이 검수
